# 4.8 Basics (and Problems) of Testing
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-8-basics-and-problems-of-testing)

Remember in [section 4.4](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-4-complex-conditions-and-nested-if-statements) we looked at a way of program design ("don't get sucked in") and showed two very different versions of the same legal date code. Once you get to conditional statements, testing becomes more complicated because now there are multiple  *paths* through our code and,  *ideally* , we need to test them all. Actually though, we can show that we can't - but we can make life easier for ourselves.

### 4.8.1 History - Alan Turing, Kurt Gödel, Rice on a Chessboard, and Checking if Programs are Correct

#### Alan Turing and the Halting Problem

Mainly now known for his work on code breaking and the AI 'Turing Test', [Alan Turing](https://en.wikipedia.org/wiki/Alan_Turing) first became famous (well 'famous' as a mathematician) in 1936 with his work on something we now call  *The Halting Problem* (the actual title of his paper was "On Computable Numbers, with an Application to the Entscheidungsproblem"). The basic idea of The Halting Problem is: given a computer program and a set of inputs for that program, is it possible to write  *another* program that would tell you if the first program halted given the specified input? Nothing as complicated as "halted and gave the right answer" -  *just halted* as opposed to running forever (an i *nfinite loop* ). Turning proved this was not possible for programs in general (for very simple ones it is but nothing realistic). And by 'impossible' we don't mean 'too expensive', 'too hard', 'not worth it' - we mean absolutely really, 100% mathematically not possible  *at all* . (He did this using  *proof by contradiction -* showing that if you assumed it was possible, you could show it wasn't possible essentially. We won't go into it but it's not that hard to follow and you will probably do it at some point). Computers as we know them did not exist them - so he wasn't talking about computers as we understand them - but the result applies even so.

#### Kurt Gödel and Incompleteness

A few years before that there was another important result. At the start of the 20th century a group of mathematicians led by a German mathematician called [David](https://en.wikipedia.org/wiki/David_Hilbert)[Hilbert](https://en.wikipedia.org/wiki/David_Hilbert) set out to try to make mathematics completely  *formal*  (you may think it obviously is, but actually it isn't). In 1929 another German mathematician [Kurt Gödel](https://en.wikipedia.org/wiki/Kurt_Gödel) demonstrated his  *incompleteness theorems -* showing that was completely impossible too, and that most problems could not be 'solved' (or at least you couldn't tell if they could be solved - or don't have a solution; or there is a solution but you can't compute it - it's debatable and beside the point because, either way, you can't do it).

***So even before computers were invented - we have these two important results saying, basically, "this is going to be a problem".***

#### Undecidable Problems

The Halting Problem is an example of something that is provably  *undecidable -* a problem which you can show there is no  *algorithmic solution* to. That is, you can't write a program to do it. The  *incompleteness* theorems of Gödel are closely related to these. That doesn't mean you can't non-algorithmically 'solve' some of these problems by mathematically proving them. But, although mathematicians don't often say this, mathematical proofs are often (not always) 'proofs' - things that convince people (mostly other mathematicians) that somethings is true (or not). They are  *not* 'computer says yes' unambiguously, cast-iron logically water-tight definite things in many cases. It was trying to  *make* them that which was David Hilbert's plan; and it was Kurt Gödel's results that showed 'not possible'.

#### Rice on a Chessboard

We can add to that something even older - the [rice (or wheat) and chessboard](https://en.wikipedia.org/wiki/Wheat_and_chessboard_problem) problem. The story goes (and to be clear it isn't true, it's just a story) that in some country, at some point in the distant past, a king offered to reward someone for some important service. And instead of asking for gold, they asked for a chess board, and for one grain of rice (or ear of wheat, it varies) to be placed on the first square, two on the second, four on the third and so on. The king thought he'd got away with it cheaply, but of course he hadn't. There are 64 squares on a chessboard, and growth is  *exponential,* so on the final square there would be 264 grains of rice (or ears of wheat), and a total of 265-1 in total on the board.  *That is nearly 37 trillion.*

Why is the chessboard relevant? Because typically between 10 and 20% of statements in code are  *branches -* either conditionals or (next chapter)  *loops. That means in a program of 1 million lines (not massive by today's standards) there are between 100 and 200 thousand places where there are (at least) two options for the 'path' code will take when executing it!* This is the chessboard problem - a repeated doubling of options (at least) every time there is a branch in the code -  *exponential* growth. Let's assume it's just 10% - there would be 2100000 possible paths of execution to test in a million lines of code - if you expressed that as a 'normal' number it would (approximately) be a 3 followed by  *over thirty thousand* zeros. If it's 20% not 10%, then that's 2200000 which has over  *sixty thousand*  zeros. And this is not a *ll possible tests* we are talking about here - only  *all possible routes through a program.* Remember in [1.10](https://canvas.swansea.ac.uk/courses/68227/pages/1-dot-10-programming-vs-software-engineering) we said that software was the most conceptually complex thing built by humans? This is why.

So:

- Fully testing anything other than the simplest programs is impossible in practice.
- Even testing all possible routes of execution through a program is impossible in practice.
- Magically writing another program to check your program is completely correct is also impossible and  *really* impossible, not just 'in practice' (you can  *mathematically prove* programs work completely - but that's very specialised, difficult and expensive so only done in extreme circumstances where you  *really* need the code to work e.g. Airbus does this for  *avionics* software).
- So in reality, we have to accept that no realistic-sized program is ever completely tested - and the only good part about that is that it's not our fault (having said that, it is our fault if we don't do the best that is practical even if it's not perfect).
- But.. there are things we can do to help ourselves make it a bit easier.

### 4.8.2 Control Flow Graphs and Reducing the Number of Test Paths

Going back to the two possible programs in 4.4 to check a legal date, one had  *far fewer* if statements than the other, and so  *far fewer* possible paths to test. We can visualise our programs to make this clearer using a  *control flow graph* (CFG)  *-* often just called a  *program graph.*

Here is the CFG for our first (and better) version:

*(image on Canvas: Good LegalDate CFG)*

And here is the one for the not so good version:

*(image on Canvas: Bad Legal Date CFG)*

We will explain a bit what this means just below - but you can see that the better one is  *far* simpler.

The key point about these graphs is where the arrows split - because those represent possible  *paths*  through the code. You can count the number of them - for the simpler one there are 4, meaning there are 16 possible paths (sequences of arrows) through the code. For the complex one there are (if I've counted properly) 26 - meaning 226 or  *just over 67 million!*

What you are looking at in these graphs is:

- **Statements are grey boxes** - all the grey boxes represent statements of code.
- **'Arrow' Boxes**  - the 'arrow' shaped boxes at the top and bottom represent the start and end of the code.
- **The arrows represent control flow**  - how we move from statement to statement and where arrows  *split* represent the  *start* of conditional statements, and where they  *join* represents the end of conditional statements. Where there is just one arrow, that means just one statement followed by another statement.
- **Colours**  - these are not really meaningful as these graphs are created by an IntelliJ plugin, and the red/green/blue colours of the arrows are dependent on the actual data the program has, which in these examples are just fixed constant values, so you can ignore them

In practice, it is not as bad as it actually looks - because many of the branches are  *not independent* because we are testing the same things (because the conditional statements in the code are checking mainly the same things - days in months etc.), especially in the complex/bad version. So in the better version, there are not really 16 possible paths: only 12. In the complex version there will be much fewer than 67 million. But (a) there will be a lot still; (b) there will be many more than in the better version; and (c) even if you didn't spot in the better version that there were only 12 real paths not 16 (which is pretty easy once you have experience) it's still only 16 (vs some massive number for the other one).

**KEY TAKE-AWAY POINT** -  *Reducing the number of places where your code branches can massively reduce the number of tests you need to do. You still won't be able to test everything in most cases, but you will be able to test a lot more of the possible execution paths.* This means your code will be easier to understand; easier to test; easier to debug; and more likely to be bug-free.

### 4.8.3 Graphs in Computer Science

As well as the control flow graphs above, a  *graph* is an important concept in Computer Science (and Software Engineering). First the 'graphs' you may be familiar with (line, bar etc) are more properly called  *charts.* A  *graph* is a set of  *nodes* or  *vertices* connected by a set of  *edges* (the arrows). For example:

*(image on Canvas: Example Directed Graph)*

This - like the control flow graphs above - is an example of a  *directed graph* because the  *edges*  (arrows) only go one way (so if you need to go in both directions between the  *nodes* (the numbered circles) then you need  *two* edges, one in each direction. More formally, a  *directed graph*

*(image on Canvas: LaTeX: G=\left(V,E\right))*

consists of:

- *(image on Canvas: LaTeX: V)*  - a set of nodes (or vertices); and
- *(image on Canvas: LaTeX: E)*  - a set of edges, where each edge is a pair of nodes  *(image on Canvas: LaTeX: e=\left(m,n\right))*  representing a connection from node  *(image on Canvas: LaTeX: m)*  to node  *(image on Canvas: LaTeX: n)* .

So for example we can represent the graph above like this:

*(image on Canvas: LaTeX: G=(V,E))*

*(image on Canvas: LaTeX: V=\left\lbrace1,2,3,4,5,6,7\right\rbrace)*

*(image on Canvas: LaTeX: E=\left\lbrace\left(1,2\right),\left(2,6\right),\left(6,4\right),\left(4,3\right),\left(4,5\right),\left(5,4\right),\left(1,3\right),\left(1,4\right),\left(7,4\right)\right\rbrace)*

Graphs can also be  *undirected* - and in that case an edge  *(image on Canvas: LaTeX: e=\left(m,n\right))*  isn't just a connection from  *m*  to  *n* , but also from n to m (i.e. you can go both ways).

Graphs are very well-understood mathematical objects, with many understood properties, and many algorithms to process and interrogate them, so being able to represent programs as graphs enables us to apply a wide range of tools to manipulate and check them.
