# 4.9 Test Coverage
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-9-test-coverage)

In this section we are going to continue with testing, and look at essentially,  *how many tests do you need to run?* This is not a simple idea and depends on what you want to achieve - and there isn't going to be a simple answer unfortunately. We explained in section [4.8](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-8-basics-and-problems-of-testing) that  *completely* testing  *everything* is going to be in practice impossible. So we might want to rephrase this:  *how many tests do you need to run to get a certain level of confidence that your code is correct?* We'll skip over what we mean by 'confidence' in this module. To do this we are going to introduce the concept of  *coverage -* that is:

***How much of your code is checked (or 'covered') by your tests?***

It turns out there are many different definitions of this - for example:

- C0 - every  *statement*  in the code is executed at least once (you might think this is enough - we have an example below to show it isn't).
- C1 - every  *path*  through the code is executed at least once (this is different to C0 and we explain why below).
- C2 - as with C *1*  but we test each part of every  *compound* conditional independently.
- C∞ - every possible combination of paths through the code have been executed (in practice this is just not feasible - sometimes you see this called C3).

We can choose one of these coverage suites (or one of many others I haven't listed) - except realistically the last one in most cases - and come up with a set of  *test cases* called (usually) a  *test suite* that meet the criteria we have chosen.

Before we get into actually writing test suites, it isn't immediately obvious how C0, C1 and C∞ are different, so we'll explain using the legal date example from [4.4.](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-4-complex-conditions-and-nested-if-statements)

### 4.9.1 Legal Date Test Coverage

The legal date code and control flow graph are repeated below.

```java
public class LegalDate {
    public static void main(String[] args){
        int month = 2;
        int day = 29;
        int year = 2019;

        int daysInMonth = 31;
        int daysInFeb = 28;

        if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
            daysInFeb = 29;
        }

        if ((month == 4) || (month == 6) || (month == 9) || (month == 11)) {
            daysInMonth = 30;
        } else if (month == 2) {
            daysInMonth = daysInFeb;
        }

        if ((month >= 1) && (month <= 12) && (day >= 1) && (day <= daysInMonth)) {
            System.out.println("Legal Date");
        } else {
            System.out.println("NOT Legal Date");
        }
    }
}
```

*(image on Canvas: Legal Date Control Flow Graph)*

- *(image on Canvas: LaTeX: C_0)*  - this means we need a set of test data that ensure that every  *node* (grey box) is visited at least once.
- *(image on Canvas: LaTeX: C_1)*  - this means we need a set of test data that ensures that every  *edge* (arrow) is followed at least once.
- *(image on Canvas: LaTeX: C_{\infty})*  - this means we need a set of tests data that ensures that every  *combination* of edges is followed.

What about C2? We'll come back to that later. Lets's try to build sets of test data for each of these classes.

### 4.9.2 C0

For this and all the other tests data sets, we need to come up with a set of values for  **month**,  **day**  and  **year**  - currently these are hard-coded as 2, 29 and 2019 but we can of course change them (or read them from the keyboard). For this first example, we are going to go slowly and carefully.

The first two statements (skipping the assignments of  **month**,  **day**  and  **year** because that's just setting our  *test data* ) in the code are the initial assignments:

```java
int daysInMonth = 31;
int daysInFeb = 28;
```

These two statements will always be executed, so every possible set of test data will 'cover' these two.

The next statement is the conditional:

```java
if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
    daysInFeb = 29;
}
```

Remember for  *(image on Canvas: LaTeX: C_0)*  we have to visit every  *statement*  - so we must have a test case that makes this test true, to ensure we do the assignment to  **daysInFeb**. But we do  *not*  have to have a case that is false (there are no else cases) because there are no statements that we would execute in that case that we don't execute when the if statement is true - C0 is about the  *statements* not the  *paths* . So we are going to pick  **month=4, day=20, year=2000.**  We can now look at those statements that will be executed by this (in bold below):

```java
public class LegalDate {
    public static void main(String[] args){
        int month = 4;
        int day = 20;
        int year = 2000;

        int daysInMonth = 31;
        int daysInFeb = 28;

        if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
            daysInFeb = 29;
        }

        if ((month == 4) || (month == 6) || (month == 9) || (month == 11)) {
            daysInMonth = 30;
        } else if (month == 2) {
            daysInMonth = daysInFeb;
        }

        if ((month >= 1) && (month <= 12) && (day >= 1) && (day <= daysInMonth)) {
            System.out.println("Legal Date");
        } else {
            System.out.println("NOT Legal Date");
        }
    }
}
```

This one test case has actually executed nearly all the statements in the code! We can come up with another test case that does the other two -  **month=2,day=30,year=2000**. This will set  **daysInMonth**  to  **daysInFeb**  (because the month is 2) and will print that it's not a legal date (because February never has 30 days) and so execute the only statements we haven't done yet. Summarising this:

| month | day | year | Expected Result |
| --- | --- | --- | --- |
| 4 | 20 | 2000 | Legal Date |
| 2 | 30 | 2000 | NOT Legal Date |

### 4.9.3 C1 - And the Problem with C0

Unfortunately C0 misses some important cases - because it doesn't follow every path. There are two possible places in this code where there is a problem, both related to the two if statements that do not have a final else (but instead end in else-if). They are this one:

```java
if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
    daysInFeb = 29;
}
```

and this one:

```java
if ((month == 4) || (month == 6) || (month == 9) || (month == 11)) {
     daysInMonth = 30;
} else if (month == 2) {
      daysInMonth = daysInFeb;
}
```

Shown in these two parts of the control flow graph:

*(image on Canvas: Checking for leap year)*   *(image on Canvas: Checking for days in month)*

In both cases the red arrow shows the path that our tests have not followed - because we had to visit every node (the grey boxes) and not follow every edge (arrow). The reason this is a problem is that there could be bugs that the code in the grey boxes are masking, and we have not run any tests that do bypass that code (the red arrows).

What bugs? How about:

```java
int daysInMonth = 32;
int daysInFeb = 30;
```

That is, we have made mistakes in the initial values of these two variables.

We now have incorrect values for the number of days in February (if it's not a leap year) and the number of days in a month (if the month is not 2, 4, 6, 9 or 11). And our test cases both miss these - because we were focussing on making sure all the  *statements* were executed (which happened to overwrite the incorrect values with correct ones), and not the  *paths* that  *skip* some of the statements. We didn't pick this up with C0 because the code we executed in those tests replaced the incorrect values with new ones, effectively 'fixing' the errors.

How do we fix these? The first one is easy - we just need a year that is not a leap year, so we can change the first test case to month=4, day=20, year=2026. This just leaves the final missed arrow - which is for months with 31 days. So we can have month=5, day=5, year=2026. Giving:

| month | day | year | Expected Result |
| --- | --- | --- | --- |
| 4 | 20 | 2000 | Legal Date |
| 2 | 30 | 2026 | NOT Legal Date |
| 5 | 5 | 2026 | Legal Date |

To be fair, in our C0 table, we could have avoided the problem with  **daysInFeb**  by picking a second test example that wasn't a leap year - but we would still have the problem with months that have 31 days even if we did that.

### 4.9.4 C∞

If you read [4.8](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-8-testing-and-conditionals) you will know that for fully testing all combinations of paths, you need 12 tests:-) but why? We need to count every possible combination of path in the code - there are 2 through the first if statement, followed by 3 through the next if-else statement and 2 through the final if-else, so it's 2 * 3 * 2 = 12. Here's an example set of tests:

| month | day | year | Expected Result |
| --- | --- | --- | --- |
| 4 | 20 | 2000 | Legal Date |
| 2 | 29 | 2020 | Legal Date |
| 5 | 5 | 2024 | Legal Date |
| 6 | 31 | 2004 | NOT Legal Date |
| 2 | 30 | 2004 | NOT Legal Date |
| 7 | 0 | 2004 | NOT Legal Date |
| 9 | 30 | 2021 | Legal Date |
| 2 | 28 | 2026 | Legal Date |
| 8 | 31 | 2025 | Legal Date |
| 11 | 31 | 2022 | NOT Legal Date |
| 2 | 29 | 2023 | NOT Legal Date |
| 12 | 33 | 2019 | NOT Legal Date |

**EXERCISE** - go though and check these are (a) giving the correct expected result; and (b) do actually cover all possible combinations of paths through the code (for part (b), notice that the first six years are leap years and the last six are not; and that for each block of six years, we have two months with 28/29 days, two with 30 days, and two with 31 days, of which in each case, one is legal and one isn't.

### 4.9.5 Is This Sensible? And What About C2?

We have some extreme examples here - we have the very small number of tests for C0, the only slightly larger number for C1 but clear evidence that it can detect more bugs than C0, and the much larger (but still only 12) cases for C∞.

Twelve test cases for C∞ isn't actually that unreasonable here - it's a do-able number. But: (a) see below; and (b) suppose there were another two if-else statements after the ones we have, one with three possible paths and one with two. In that case we'd have to multiply the number of tests by 3 * 2 = 6, and there would be 72 of them. Still doable but you can see that this number will rapidly grow out of control. Also, is it the case that C∞  will actually catch more bugs than C1? Or enough more bugs to be worth the trouble (when we have bigger blocks of code and  *much* bigger test sets if we want to do C∞ )? The answer usually is 'no'.

Another point to make is that we are arguably 'cheating' and cutting the number of possible paths by using  *compound* boolean statements in our code. So something like:

```java
if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
    daysInFeb = 29;
}
```

from the point of view of testing is really this (note I'm NOT saying you should write it like this!)

```java
if (year % 4 == 0) {
    if (year % 100 != 0) {
        daysInMonth = 29;
    }
} else if (year % 400 == 0) {
    daysInMonth = 29;
}
```

which has six paths not two:

*(image on Canvas: Compound Conditional Control Flow Graph)*

because we should check years that are/aren't divisible by 4; are/aren't divisible by 100; and are/aren't divisible by 400 separately (and do the same for all the other if-else statements in the code too). This is what C2 testing means - if you have a statement like this:

```java
if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
    daysInFeb = 29;
}
```

Instead of having two tests (one for which the condition is true and one for which it is false), you need to consider each of the parts individually:  **year % 4 == 0**,  **year % 100 != 0**  and  **year % 400 == 0**. This will obviously be a lot more cases.

### 4.9.6 C∞ Revisited...

Having looked at C2 you might not think we have sort-of 'cheated' with C∞ because C∞ is supposed to be 'ultimate' testing somehow, and we didn't test all parts of all conditional statements for that. What happens if we do? The number of cases goes up massively. For checking if a year is a leap year, there are no longer just two cases but eight (three sub-expressions that can either be true or false, so 2 * 2 * 2 = 23 = 8). And the number of other cases goes up too - so instead of 2 * 3 * 2 it's now 8 * 32 * 8 =2,048 which is obviously unreasonable. (The 32 comes from every combination of each possible == expression when checking for each one being true or false individually, and there are five == checks: 25 = 32 though to be fair we could probably cut that down a bit as many are  *mutually exclusive* - i.e. a month can't be both 4 and 7 at the same time etc. *)*

### 4.9.7 In Practice...

Here is what you should in practice do.

#### Try to Test Small Blocks of Code as You Write Them.

This is partly behind the idea of  *unit testing* which we will get to later. So lets go back to the working out if it's a leap year example. To check that you are calculating if a year is a leap year or not properly,  *first* write this code:

```java
if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
    daysInFeb = 29;
}
```

and test that  *on it's own* with leap years that are divisible (or not) by 4, 100, 400  *before* you combine it with the rest of the code (i.e you basically do a C2 test of  *that piece of code on its own* ). Also, do the same with the other two blocks of code that work out how many days a month should have, and finally decide if a day is legal or not. That way, when you combine them, you  *don't* have to come up with lots of extra test cases to check all possible cases of years divisible by 4, 100, 400; and all four possible months that could have 30 days; and February... - leading to a massive number (2048...) of test cases  *because you have already checked this independently and you KNOW, say, that your leap year calculation is correct (because you've tested it) -*  meaning when you are testing it all together you only need to do tests that do and don't have leap years, not all possible  *kinds* of leap year. That way, as well as not having large blocks of code to test - and find bugs in - you need to run much fewer test cases.  **A key part of testing it to make sure  *small* pieces of code are correct before you combine them into larger pieces of code.**

#### Most Developers use C1 or at most C2

I would suggest C1  *but I would also suggest you do the above: test very small blocks thoroughly at at time.* I would  *also* suggest don't get hung on Cthis vs Cthat. If you think you need some extra cases to check something or another, just do them.

#### Boundary Values

One thing we haven't done in the examples above is consider  *boundary* values - for example, legal months are 1 to 12, so boundary values in this case would be 0,1,12 and 13. That is, those cases just above and below the 'boundary' for a legal month number. I would probably add in some additional cases to handle boundary values, even if I was already at, say C1.

#### Working Out Test Cases

It's not always easy to work out test cases - you need to be sure you have met the test criteria set (either by your or someone else - probably your boss...) and you also need to know what the outcome is supposed to be. I've said this before  *but there is no point in tests when you don't know what the answer is supposed to be.*

#### Most Bugs are Local

Usually a bug is localised in the code - it is rare that they are caused by, say, following one branch at one if statement, followed by another branch at another if statement, followed by... etc. So the benefits of testing all possible combinations of paths are limited (especially compared to the costs) - which is why just checking all paths is normally considered enough.

#### Use API (Library) Operations

Don't 'reinvent' things - for example, suppose you wanted to check if the user entered a 'Y' in response to a yes/no question. You could do  **inputVal.equals("Y") && inputVal.equals("y")**. But then to fully test it, you'd need to check it was "Y", yes or no; "y" yes or no; or neither - so five tests for C2. But if you just used the built in operation equalsIgnoreCase it would just be  **inputVal.equalsIgnoreCase("y")**  - so only two cases (it's either true or not). You can reasonably assume that library or API ( *application program interface* ) operations are well-tested and correct.

#### Depends on Certification

Where you might have to do more rigorous testing is when you need to meet specific  *certifications.* This is common in  *safety-critical applications -* do you want to get on a plane where the software has been tested to C1?
