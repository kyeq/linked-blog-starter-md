# 4.4 Complex Conditions and Nested If Statements
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-4-complex-conditions-and-nested-if-statements)

You can use Boolean operators - &&, ||, ! etc. – to create conditions that are as complex as you want – but you probably don’t want to because they can get hard to read. For example, consider  *leap years.* The common perception is that leap years happen every four years –  *but this is not quite true.*  The actual rules are:

- Years that are divisible by 400  **are**  leap years.
- *Years that are divisible by 100 but not 400  **are not**  leap years.*
- All other years divisible by four not covered by the two cases above  **are**  leap years.

As you can see, it’s a bit more complex – so here’s some code to tell if a year is a leap year or not:

```java

if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
     System.out.println("Is a leap year");
} else {
     System.out.println("Is not a leap year");
}
```

This code is explained here:

> [!note] There is a video for this on the Canvas page.

This works but it’s a bit ‘dense’ and hard to read. We might want to break it up a bit to make it clearer. One way to do that would be to use some Boolean variables; another would be to use  *nested*  if statements – one if statement inside another.

```java
//All leap years must be divisible by 4...
if (year % 4 == 0) {
     //Ones divisible by 400 are leap years...
     if (year % 400 == 0) {
          System.out.println("Is a leap year");
     //But ones divisible by 100 and not 400 are not
     } else if (year % 100 == 0) {
          System.out.println("Is not a leap year");
     //All others divisible by 4 are leap years
     } else {
          System.out.println("Is a leap year");
     }
//Anything not divisible by 4 is not a leap year
} else {
     System.out.println("Is not a leap year");
}
```

**NOTE**  this is NOT in my opinion the best way to write this code - that's in the video in 4.4.1 below which is a VERY important one to watch.

> [!note] There is a video for this on the Canvas page.

We’ve broken the logic into parts, and that’s allowed us to add comments to help explain it – in the previous case it would have been harder because the comments could not go ‘within’ the logic. In this particular example, one thing I don’t like is the repeated messages – we have to put each one in twice which violates the DRY ( *don’t repeat yourself* ) principle. But we can fix that:

```java
static final String NOT_LEAP_YEAR = "Is not a leap year";
static final String LEAP_YEAR = "Is a leap year";...
//All leap years must be divisible by 4...
if (year % 4 == 0) {
     //Ones divisible by 400 are leap years...
     if (year % 400 == 0) {
          System.out.println (LEAP_YEAR);
     //But ones divisible by 100 and not 400 are not
     } else if (year % 100 == 0) {
          System.out.println (NOT_LEAP_YEAR);
     //All others divisible by 4 are leap years
     } else {
          System.out.println (LEAP_YEAR);
     }
//Anything not divisible by 4 is not a leap year
} else {
     System.out.println(NOT_LEAP_YEAR);
}
```

In this particular case, this might all be going a bit far – the nested code is probably easier to understand for new programmers in this case; but the first example is not  *that* hard. But there are examples where simply trying to build one large condition would be very complex and hard to understand.

*In general, nested if statements are more 'complex' than ones that are not - if you check out the final video on this page you'll see we come up with a solution to a complex problem that does not have nested if statements. But that isn't to say they are "wrong" and if in your opinion they are the clearest solution to a problem, there is no reason not to use them.*

### Exercises

- Try rewriting the nested if - else version above so that the shorter part (the 'not leap year part" at the end is first - in practice I think if-else statements where the shorter part is first are normally clearer.
- Try rewriting the code above so it uses a sequence of if-else - not one nested inside another (hint: check for 400 first, then 100, then 4).
- Try writing a 'hybrid' version - which uses, say, the boolean && operator to work out if a year is divisible by 4 but not 100, but deals with the 400 case separately using an else - you will need to think carefully about the order you do things.

### KEY POINT: Using Boolean Logic, Boolean Variables and Nesting for Complex Conditions

If you have complex conditions that need to be evaluated for if statements, consider Boolean logic, Boolean variables, or nested if statements – of a combination of these. What should you choose in each case? That really depends on the example and your judgment – you will get better at judging what’s the best option as you gain experience.

In practice, I don't think that the solution above is the best way to represent the calculation of a Leap Year - both because I don't think it is the clearest and because it's not the one I would come up with if I applied some basic program design principles.

So keep trying to improve your code - don't just think "it works, it's fine"! In other words, always try to  *refactor* what you write to make it better.

### 4.4.1 Program Design Example and Principle - REALLY IMPORTANT ONE TO WATCH AND READ!

The video below walks through an example of writing a program that checks if a date - day, month, year - is legal, accounting for leap years. In summary:

- Try to break the problem into parts.
- Solve the part you are doing - don't get 'sucked in' to solving the other parts (introduce extra variables as 'place holders' for the parts you haven't done yet).
- If you don't know how to solve the whole problem, solve the bit you can, and then try to work on the next bit.
- **This is a bit longer than my usual videos - but it's REALLY worth watching in my opinion.**

> [!note] There is a video for this on the Canvas page.

Here's the complete code from this video:

```java
public class LegalDate {
    public static void main(String[] args){
        int month = 2;
        int day = 29;
        int year = 2019;

        int daysInMonth = 31;
        int daysInFeb = 28;

        if ((year % 4 == 0) && (year % 100 != 0) || (year % 400 == 0)) {
            daysInFeb = 29;
        }

        if ((month == 4) || (month == 6) || (month == 9) || (month == 11)) {
            daysInMonth = 30;
        } else if (month == 2) {
            daysInMonth = daysInFeb;
        }

        if ((month >= 1) && (month <= 12) && (day >= 1) && (day <= daysInMonth)) {
            System.out.println("Legal Date");
        } else {
            System.out.println("NOT Legal Date");
        }
    }
}
```

This is obviously  *really* long and  *really* repetitive - and probably in reality this would be spotted and would not be this bad. BUT I DO see code like this in coursework and labs every year. And it is caused by the mindset of "I need to solve problem 1... but, oh, to do that, I also need to solve problem 2" - and then going ahead and solving problem 2 in the middle of doing problem 1. DO NOT DO THAT - think "I will come back to that, and in the meantime I will put in a variable with some reasonable value, which I'll come back and work on later."

### 4.4.2 Code Smells and If-Else

One of the 'standard' code smells in most people's lists is  *repeated code.* Arguably, in the nested example above, we are repeating code - the  **println**  statements. Which would make the first example better than the second. I sort-of agree with this - but you can always (and probably should) make the repeated strings constants, and the code smell to  *really* avoid is repeating the  *condition.* So, for example, if we ended up with code that checked if the year was divisible by 4 more than once, then something would definitely 'smell' and we should definitely  *refactor* the code.

(There are programmers who think that  *any* if-else should be considered a  *potential* code smell - and that you should work to try to get rid of them. That's a bit advanced for us right now though.)
