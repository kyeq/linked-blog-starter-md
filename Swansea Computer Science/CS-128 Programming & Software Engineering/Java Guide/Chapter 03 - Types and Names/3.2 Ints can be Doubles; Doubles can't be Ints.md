# 3.2 Ints can be Doubles; Doubles can’t be Ints
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/3-dot-2-ints-can-be-doubles-doubles-cant-be-ints)

One important issue when dealing with different types of numbers - ints and doubles - is what happens if we try to  *mix*  them.

Notice in the first divide example above the answer printed is 2.0, not 2. Even though 10/4 involves only integers, and integer division, because we’ve said the variable mystery is a double, Java converts it for us. This makes sense – we can always represent an int as a double because, mathematically, the Integers are a subset of the Real numbers.

But the same is not true the other way round. We’re going to be using a version of the same program above in this section, and to keep things shorter I’ll only show the single important line that does the arithmetic.

If we change the important line in our example from the previous section where we divided 10 by 3 to store the result in an int:

```java
int mystery = 10/4;
```

We get 2 – which is fine since 10 and 4 are integers, we are doing integer division, and so we get an int as a result. But if we change it to:

```java
int mystery = 10/4.0;
```

(or use the either of the other versions) we get:

**XXX.java:3: error: incompatible types: possible lossy conversion from double to int**

**int mystery = 10/4.0;**

because, quite naturally, since 10/4.0 is no longer an integer division (because 4.0 is not an integer) and the result is 2.5, we cannot store the result of this calculation in an int.

What if we change it so that the result  *is* an int – by changing 4.0 to 5.0 (because 10/5=2)?  ***It still doesn’t work***  *– because in general, Java cannot know when it compiles a program that the result will always safely be an integer.*

What if we really want to force this to happen? We can by using casting:

```java
int mystery = (int)(10/4.0);
```

We’ve used brackets to make sure the cast to the int type applies to the result of the operation – in this case, it prints 2. Casting a double to an int always throws away the non-integer part.

## KEY POINT – Careful Mixing Integers and Doubles

Though you can always store the result of an integer operation in a double, you cannot do the opposite (and be careful with integer division and doubles – force one of the operands to be a double to be safe).

### Representing Doubles

So far we’ve written down doubles simply: for example, 4.0. But this is not going to be convenient for very large or very small numbers. You should be familiar with  *scientific notation:* a x 10b – for example 1 x 102 (which is 100.0), or 5.4 x 10-4, which is 0.00054). In Java just replace x10 with e: 1e2 is 100; 5.4e-4 is 0.00054. The ‘e’ stands for  *exponent*  – in 1e2 2 is the  *exponent* , and 1 is the  *mantissa* .

### The Math Library

If you are using doubles you might well want to use more advanced mathematical operations – we won’t (much…) but if you do, you can find the documentation for the library at the same URL we found Scanner. So if you want, for example, to raise a number to a power – there is no direct operator for it, but you can do it with the Math library.

### Advanced Aside: Why are they called double?

This is for historical reasons. In the early days of computers only integers were available, and if you wanted to do computations on non-integers, you had to keep track of the decimal point yourself. So for example if you wanted two decimal places, when you wrote 1234 it would really represent 12.34. You had to keep track of this yourself (and it was obviously a nuisance, complex and prone to errors). It was called  **fixed-point arithmetic**. Fairly quickly, implementations that allowed the computer to keep track of this were developed - the decimal point would then move, or  *float* . Hence this was called  **floating-point arithmetic**. Many programming languages had a datatype called  **float**  to represent these numbers. The trouble in Java (and many languages) is that they only used 32 bits to represent them (the same as an int). This restricts the range of numbers and their accuracy (so as you do arithmetic on them, the errors grow quite quickly). To handle this most languages also had a type that used 64 bits, or  **double-precision floating point**  - hence  **double**.  *Although Java has a float type there is no good reason to ever use it instead of double in this module (so please don't).*
