# 6.9 Loop Test Coverage
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/6-dot-9-loop-test-coverage)

We looked at  *test coverage* earlier - but at that point we hadn't done loops. Does this make a difference? The short answer is  *no not really -* but people often take some convincing that's true. So we'll look at an alternative coverage model called Ci(k).

### 6.9.1 Ci(k) Test Coverage

Another possible definition of test coverage is Ci(k) - that is, in addition to the requirements of C1, all loops are executed zero, one, and up to k times. So for example Ci(3) would mean all loops executed, zero, one, two and three times.

As before with testing, we need to think about  *practicality -* often called  *tractability.* We are also going to again think about  *boundary cases.* The obvious boundary cases for a loop are: it doesn't execute at all; and it executes once. Those two possibilities also conveniently cover the requirements for C1 above (you will follow all the arrows in a control flow graph if you do that). We would also fairly commonly add a 'normal' case too - the loop executes twice. So Ci(2) looks like a reasonable compromise. Let's look at an example from earlier in the chapter - working out how much money you have after a fixed number of years, given a starting balance and an interest rate. We have changed it slightly so that the number of years is a variable (we will need to change that to generate different test cases):

```java
public class SimpleInvestment {
    static final double INTEREST = 5.0;
    static final double MULTIPLIER = 1 + INTEREST/100;
    static final int years = 1;

    public static void main(String[] args) {
        double balance = 10000.0;
        for(int i = 0; i < years; i++) {
            balance *= MULTIPLIER;
        }
        System.out.println(String.format("Amount: %.2f", balance));
    }
}
```

Here's the control flow graph:

*(image on Canvas: Loop Control Flow Graph)*

In this diagram, the dark grey box is the for-loop itself, and the light grey box is the body of the loop  **balance *= MULTIPLIER.**

- The first thing to note it that loops just mean that there are arrows that return to earlier points in the graph - that is, there are  *cycles.* But loops don't introduce anything new beyond that (so our C0, C1 concepts still make sense).
- The second thing to note is that C1 requires that we follow all the arrows - so that  *already* includes the case when the loop is not executed at all (the red arrow) and the case when it's executed once (the green arrow followed by the blue arrow. You could even argue that just executing the loop once is C1 because that would be green arrow; blue arrow; and then red arrow to exit the loop, and in this case C0 is the same as C1 (because executing the loop goes through both nodes of the graph - the dark and light grey ones.

So in this case, being reasonable, the two sets of test suites for C0 and C1 are:

| years | result |
| --- | --- |
| 1 | 10500.0 |

| years | result |
| --- | --- |
| 0 | 10000.0 |
| 1 | 10500.0 |

And for the Ci(2) case (where we execute loops 0, 1 and 2 times):

| years | result |
| --- | --- |
| 0 | 10000.0 |
| 1 | 10500.0 |
| 2 | 11025.0 |

Is it worth it in this case? Or should we stick to C1 (or even C0).  *In this case* I don't think it's worth doing Ci(2) but I  *don't* think C0 is sufficient because it skips the important  *boundary* case of zero iterations of the loop. Also, although we can exercise  *judgement* and decide what tests are needed, C1 is generally in line with typical testing practice.

### 6.9.2 Issues with Ci(k)

There are some cases where Ci(k) doesn't work. For example with do-while loops:

```java
import java.util.Scanner;

public class GuessTheFruit2 {
	public static void main(String[] args) {
		final String SECRET_FRUIT = "lemon";

		System.out.println("Welcome to Guess the Fruit!");

		Scanner in = new Scanner(System.in);

		String guess;

		do {
			System.out.print("What's your guess: ");
			guess = in.next();
		} while(!guess.equals(SECRET_FRUIT));

		System.out.println("Congratulations! It is a " + SECRET_FRUIT);
	}
}
```

They are always executed at least once.

Also this other earlier loop:

```java
/**
   This program computes the time required to double an investment.
	It uses a loop which goes round (*iterates*) once per year
   Because we don't know how many years it will take, we use a while loop.
*/
public class DoubleInvestment
{
   public static void main(String[] args)
   {
     	final double RATE = 2.0;	//Interest rate
     	double balance = 10000;		//Starting amount
     	final double TARGET =  balance * 2;
     	int year = 0;

       // Count the years required for the investment to double
       while(balance < TARGET){
			double interest = balance * RATE / 100;
			balance += interest;
			year++;
			System.out.println("After " + year + " years you have " + balance);
		}

		// Print out the result
		System.out.println("The investment doubled after "
				+ year + " years.");
   }
}
```

In this case it's only possible to make it execute either zero times (by setting balance to zero) or 36 times - because it always takes 36 years for the initial amount to double with a 2% interest rate.

Also, you can contrive programs where it's impossible to force loops to execute a set number of times. In this case, you can make the  *first* loop execute 0, 1 or 2 times (by changing the value of loop). But the second loop will always execute loop*2+3 times (so you can't make it execute 0, 1 or 2 times in any circumstances):

```java
public class WeirdLoop {
    public static void main(String[] args) {
        int numLoops = 2;
        for(int loop = 0; loop < numLoops; loop++) {
            System.out.println("Loop " + loop);
        }
        for(int loop = 0; loop < numLoops*2+3; loop++) {
            System.out.println("Loop " + loop);
        }
    }
}
```

### 6.9.3 KEY POINT - Test to AT LEAST C1

**Minimally you should  *always* test to C1.**

*BUT*

**Don't think you cannot add extra test cases if in your judgement it's necessary (or you want to be cautious)**

**What NOT to do is to just make up some random data - DESIGN your tests to check as many possible  *categories* of cases as possible.**

For example, going back to the legal date example, making  *two* different test cases for 29th February on two different leap years is - provided you are sure you are correctly identifying leap years - pointless.
