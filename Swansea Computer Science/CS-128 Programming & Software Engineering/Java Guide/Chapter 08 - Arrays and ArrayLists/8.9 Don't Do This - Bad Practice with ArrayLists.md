# 8.9  Don't Do This - Bad Practice with ArrayLists
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/8-dot-9-dont-do-this-bad-practice-with-arraylists)

When you declare an ArralyList, you can actually leave the <String> bit out altogether: So instead of, say:

```java
ArrayList<String> names = new ArrayList<>();
```

You can write  **(but don't)**:

```java
ArrayList names = new ArrayList();
```

And you will often see this in old text books (still in the library, unfortunately) and web sites about Java (from early versions of Java, before you could say what type the data should be).  **But you shouldn’t do it**. Doing so says ‘make an ArrayList that can contain  *anything’*  – which seems handy  **but is very bad practice**  (unless you are in the very rare case that this is what you actually need to do - and the chances are this will  *never*  happen to you)  ***because it means a whole class of errors can no longer be caught early by the compiler but will seem to 'work' - but are really waiting to crash your program at some random point in the future* .**

Here's an example of doing it the 'bad' way:

```java
public class ArrayListNoNo {
    public static void main(String[] args) {
        ArrayList arrayListData = new ArrayList();
        String[] arrayData = {"lemon", "orange",
                        "pineapple", "kiwi", "apple"};

        //Copy Array to ArrayList
        for(String elem : arrayData) {
            arrayListData.add(elem);
        }

        //Print out ArrayList
        for(int i = 0; i < arrayListData.size(); i++) {
            String elem = (String) arrayListData.get(i);
            System.out.println(elem);
        }
    }
}
```

The lines that are different are in  **bold.** The first one  *should*  be:

```java
ArrayList<String> arrayListData = new ArrayList<>();
```

And the second one:

```java
String elem = arrayListData.get(i);
```

The first line in our ‘wrong’ program doesn’t tell Java that our ArrayList will only contain strings so (a) it can contain anything; and (b) we need to tell it that it actually has String data in it when we read the data to print it – which is what the (String) in brackets does in the second line in bold does (this is a  *type cast -* it 'forces' data to be a particular type). We need to add this here because otherwise Java can't what the data should be - because when we added it, it got turned into a generic  *Object* and the fact that it was a String was lost.

The problem is that we can put in this line and add an  **int** to our ArrayList (which we only  *want* to be able to hold strings):

```java
arrayListData.add(5);
```

And  *the code will compile and run –* it will, however, crash when it tries to turn the integer 5 into a String because Java can't do that. The trouble is that in real, complex, programs not all the lines of code are run every time – so it’s easily possible for a bug like this to lay hidden and not be found.

### Exercise

Try swapping the two lines in bold with the two ‘correct’ lines directly above; and then try putting in the line that adds an integer – you will get a compiler error because Java now knows that only String is allowed in the ArrayList. This is good because the compiler  *always* checks  *all the code.*

## Compiler Warnings – Pay Attention to Them!

If you actually compile the “bad” code above, and pay attention to what the compiler output, you will see that it (a) compiles but it (b) gives you a  *warning.* This warning says:

**Note: ArrayListNoNo.java uses unchecked or unsafe operations.**

**Note: Recompile with -Xlint:unchecked for details.**

You have two choices at this point:

- You can say “hey, it’s only a warning – it still compiles”. This is the  **wrong answer!**  *Compiler warnings are another example of a  **code smell** and  **technical debt:**  things that are (a) wrong and (b) will 'cost' you later.*
- You can actually *follow the instructions*  it’s giving you. It’s telling you to recompile your code like this:

javac –Xlint:unchecked ArrayListNoNo.java

where –Xlint:unchecked is a  *compiler switch*  or option, that tells the compiler (in this case) to tell you about any code that does not check the type of the data it deals with. Two things:

- the name ‘lint’ is from an old in-joke - you’ll find it refers to “… the name of the undesirable bits of fiber and fluff found in sheep's wool.”
- You can just type –Xlint and leave off the “:unchecked” part.
