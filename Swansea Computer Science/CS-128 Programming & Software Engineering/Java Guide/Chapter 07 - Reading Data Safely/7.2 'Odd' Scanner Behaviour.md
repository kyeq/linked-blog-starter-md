# 7.2 'Odd' Scanner Behaviour
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/7-dot-2-odd-scanner-behaviour)

In the past I've had a lot of questions about some apparently 'odd' behaviour with Scanners and this section is intended to explain what is going on.

> [!note] There is a video for this on the Canvas page.

A Scanner reads 'tokens' - chunks of text - separated by 'separators'. By default 'separators' are  *whitespace*  characters - space, tab, or newline (you can change this if you want but you won't need to in this module). Whenever you call a Scanner method (or at least most of them) it skips past any 'separators' until it gets to a 'token' - depending on the method, it may either read and return the 'token' or crash if the 'token' doesn't match some pattern. For example, if you use nextInt() the 'pattern' is that the token has to be an integer. This means that if you call nextInt() three times in a row, you will successfully read  *both*  the following input patterns:

123

456

798

and

123 456 789

That is  *either*  the input can be on different lines;  *or*  it can be separated by spaces (and it can be multiple spaces that separate the characters) because in both cases the input is a sequence of 'tokens' separated by 'separators'.

The confusion arises when you start to also use nextLine() - because this works slightly differently. The difference between next() and nextLine() is that next() will skip any 'separators', then only read one 'token', and then stop when it gets to a 'separator'. So given the line

Lemons are the best fruit <newline>

where <newline> represents the 'newline' character, next() will only read 'Lemons'. On the other hand, nextLine() will read the whole thing - 'Lemons are the best fruit'  **and also the newline that follows it**. This is because nextLine() keeps reading text up to and including a newline; while next() (or nextInt(), or nextDouble() etc.)  **will only read up to and not including the 'separator' that follows the next token in the input.**  So given the input

Lemons<newline>

next() will just read Lemons and  **not**  the newline; while nextLine()  *will read the newline as well*

Now suppose you have the following input:

1234<newline>

Lemons<newline>

and suppose you're trying to read this with the following code:

```java
Scanner in = new Scanner(System.in)
int someNumber = in.nextInt();
String someString = in.nextLine();
```

The call to nextInt() will read the number 1234 but  **not**  the newline; the call to nextLine() will read everything up to and including the next newline - which, of course, is  *the empty string*  immediately after 1234 because nextInt() did not read the first newline. This means that someString contains an empty string, and Lemons hasn't actually been read yet. The solution is this:

```java
Scanner in = new Scanner(System.in)
int someNumber = in.nextInt();
in.nextLine(); //'throw away' the empty string after the number 1234
String someString = in.nextLine();
```
