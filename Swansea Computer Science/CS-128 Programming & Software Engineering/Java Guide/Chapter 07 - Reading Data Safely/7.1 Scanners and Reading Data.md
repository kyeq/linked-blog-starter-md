# 7.1 Scanners and Reading Data
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/7-dot-1-scanners-and-reading-data)

***Note***  *: some example programs are from, or based on, examples from Java for Everyone (C Horstmann), the course text.*

So far we’ve used the Scanner library to read in strings and integers, and we’ve observed that if you try to read in an integer and the user types something that is  *not* an integer, then your program will crash. We really need to do something about that.  **Protecting your program against incorrect (and potentially dangerous) input is the first step in establishing security - not doing this is another form of  *technical debt*  which you will have to 'pay' later. It is also very irresponsible as it compromises the safety and security of your code, opening it up to unauthorised access to data, which is a violation of professional ethics.**

Fortunately, there are several ways to do this.

- **Check for the Error First**  – the  *much preferred*  (in thismodule and generally by a lot of programmers) way to do it is to check  *first*  to see if there’s going to be a problem – Scanner provides ways to ‘sneak a look ahead’ and see what the user’s typed before we actually read it in.  **This is how I want you to do it in this module**  – it is shorter and does not rely on you using features of the language we are not doing yet.
- **Catch the Error**   **- skip this one on first reading if new to programming ( *and don't actually do it even if you aren't!* )**  **–**  we can ‘trap’ the error and fix it. Java includes features to do this, called  *exception handling,* based on the keywords try and catch (essentially you ‘try’ something and if it goes wrong you ‘catch’ the error). Exceptions and handling them is part of the CS-115 module **.**   **But please do NOT do it like this - it is VERY VERY BAD PRACTICE.**  Sometimes tutors and lab demonstrators (and maybe some lecturers...) will suggest it – but it's a bad idea for three reasons.
		- First it’s an advanced technique, that’s easy to get wrong (and people commonly do in attempting coursework). It’s also easy to write code that is bad practice – for example, having far too much code in the ‘trying’ part; or doing nothing in the ‘catching’ part, both of which are not good.
		- The code you write usually ends up being longer.
		- ***Most importantly there's a strongly-held view (by many highly experienced programmers) that using exceptions in routine data validation is an abuse.*** For example,  **Joshua Bloch's Effective Java Item 69:**   *Use exceptions only for exceptional conditions* . Simply, an 'exception' is just that - something that is 'exceptional' (i.e. an actual error of some kind). Users typing in the wrong thing is not 'exceptional' - it's normal and expected.  **So DON'T use exception handling for this.** Having said that, you will find programmers who think this is fine - but they are not marking your coursework:-)

We’ll illustrate the technique with integers – but you can also do it with other types of data too. The key to the approach is a method that forms part of the Scanner library called hasNextInt(). This does the following.

- If the user hasn’t typed any input yet, it waits.
- Once they do type something, it checks to see if it’s an integer.
- If it is, it returns true; otherwise it returns false

We can use the true/false result from this to decide if we really want to read in the value or not – hasNextInt() doesn’t actually read it in; it just checks to see if it’s the ‘right’ type. Here’s a program based on this:

```java
import java.util.Scanner;

public class InputInteger {
    public static void main(String[] args) {

        Scanner in = new Scanner(System.in);
        int input;

        System.out.print("Enter an integer: ");
        while(!in.hasNextInt()){
            System.out.println("Try again.");
            in.nextLine(); //'Throw away' wrong input
        }
        input = in.nextInt(); //actually read the integer
        System.out.println("Thank you. You typed: " +
            input);
    }
}
```

We use the while loop to check that the user has typed an integer:

```java
while(!in.hasNextInt()){
```

Is true as long as the input is  *not* an integer – because ‘!’ means  *not.* So the body of the loop needs to:

- Tell the user they have typed in the wrong thing.
- ‘Throw away’ the ‘wrong’ input – remember we haven’t read the input yet – just checked what it is. So the input is still sitting there, ‘unread’ The line in.next(); reads it in but doesn’t save it anywhere – it just discards it. Because in.next() just treats the (incorrect) input as a String not an integer, it doesn't crash.

This while loop continues as long as the input is not an integer – it will only finish if the input (waiting, unread as yet)  *is* an integer. At this point, it’s safe to read it with:

This works fine for integers – but what about other data, like doubles, or boolean? There are also methods to check to see if the data waiting to be read is a double (hasNextDouble()) or a Boolean (hasNextBoolean()) – and methods to actually go and read in doubles and booleans (nextDouble() and nextBoolean()) once you’ve checked.

### 7.1.1 Reading and Checking Specific Strings

Because any string of characters is a String, there’s no way our programs can crash if we type the wrong thing. But we still often what to ‘force’ users to type one of a specific set of strings – for example “yes” or “no”. We saw code to do this in the Chapter 6 on Loops when we talked about Do Loops. However, it bears repeating because it’s important. You should use code like this:

```java
String input;
do {
     System.out.print("Enter either yes or no.");
     input = in.nextLine();
} while (!input.equalsIgnoreCase("yes") &&
    !input.equalsIgnoreCase("no"));
```

(Or, better, the version that used  *static*   *final*  (constant) variables for “yes” and “no”).

Of course, just reading “yes” or “no” isn’t very useful – you generally want to either do something, or not, depending on what the user typed. The most common ‘pattern’ for code like this is  *two*  loops – one inside the other ( *nested loops* ). Here’s an example

```java
//Loop that does 'something'
String input;
do {
     //Code that does the 'something' left out

     System.out.println("Do you want to continue?");
     do {
          System.out.print("Enter either yes or no.");
          input = in.nextLine();
    } while (!input.equalsIgnoreCase("yes") &&
             !input.equalsIgnoreCase("no"));
} while (input.equalsIgnoreCase("yes"));

```

The inner loop checks to see if the user types “yes” or “no”; the outer loop carries on as long as they type “yes”.

### LAZY SHORTCUT – DON’T DO THIS

When writing code like the loop above, it’s very common to see people leave out the inner loop and just write:

```java
String input;
do {
     //Code that does the 'something' left out
     System.out.println("Do you want to continue?");
     System.out.print("Enter either yes or no.");
     //Inner loop left out!
} while (input.equalsIgnoreCase("yes"));
```

The problem with this is the code will assume  *anything* other than “yes” means “no” –  *including* mistakes the user might make while trying to type “yes!”. So  *don’t do it.* As well as being a poor User Experience, it's a potential security hole (assuming something about input).

### Advanced Aside - How do we check something before we read it?

We said above that e.g. hasNextInt() will check to see if the input waiting to be read is an integer before actually reading it. This seems impossible if you think about it - how can it check it without reading it? The answer is it doesn't. It has already actually been read at that point as a String (so it can't crash) and stored in an internal variable (often called a  *buffer* ) inside the Scanner you created. The hasNextInt() method just checks it in that variable, and nextInt() just reads it from that variable and tries to convert it (called  *parsing* ) to an int.

### 7.1.2 Checking Numbers

A very common condition is to need to read in a number that meets a specific condition - let's say between 1 and 100 inclusive. There are two things going on here:

- Making sure the user types a number.
- Making sure it's between 1 and 100.

Remember DON'T GET SUCKED IN!

It's easy to try to do both of these at once and end up with at best messy code and at worst code that's wrong. So DIVIDE IT INTO TWO PROBLEMS and SOLVE THEM SEPARATELY.

#### Problem 1: Reading an Integer

We have already done this above:

```java
Scanner in = new Scanner(System.in);
int input;

System.out.print("Enter an integer: ");
while(!in.hasNextInt()){
        System.out.println("Try again.");
        in.nextLine(); //'Throw away' wrong input
}
input = in.nextInt(); //actually read the integer
System.out.println("Thank you. You typed: " +
        input);
```

Nowwe  *definitely* have an integer so we need to do the second part.

#### Problem 2: Checking the Integer

```java
Scanner in = new Scanner(System.in);
int input;

do {
    System.out.print("Enter an integer: ");
    while (!in.hasNextInt()) {
        System.out.println("Try again.");
        in.nextLine(); //'Throw away' wrong input
    }
    input = in.nextInt(); //actually read the integer
    System.out.println("Thank you. You typed: " +
            input);
}while (input < 1 && input > 100);
```

I've put the new part in bold and italic to separate it out. It's not  *quite* as good as the legal date example, where we end up with three separate parts of code each solving one problem after the other, because in this case we do have a nested loop. But we do also have a clear division between the inner one (get an integer) and the outer one (check the integer).

#### How NOT to do it...

It's common to get this wrong - and there are two common problems.

- Assuming that the input can only be wrong the  *first* time it's entered - that is, a user will only enter a non-integer by mistake once, and the second time it will definitely be an integer. This is obviously not true.
- Getting sucked in - this does not mean the code doesn't work; just that it's not as good (at least IMHO).

Here's an example:

```java
do {
    System.out.print("Enter an integer: ");
    if (!in.hasNextInt()) {
        System.out.println("Try again.");
        in.nextLine(); //'Throw away' wrong input
    } else {
        input = in.nextInt(); //actually read the integer
        System.out.println("Thank you. You typed: " +
                input);
    }
} while (input < 1 && input > 100);
```

This is not dire and its  *control flow graph* needs exactly the same number of tests as the first one. But it does not separate out the two tasks - get an integer; make sure it meets the required conditions - as well, because the if statement is involved in both.

### 7.1.3 Reading Input, Security and User Experience

We have shown some code above that will stop incorrect input being accepted - we can write whatever conditions we want to check that the data is something we are prepared to accept - and this is good  *security* practice. A very basic and easy to do (but often not done...) principle of security is to  *always check input.* DON'T assume it will be OK (or that someone else will check it) - because many security issues start with cleverly-created illegal input.

The trouble is, the code we have shown above doesn't have a very good  *user experience (UX) -* because there is no way for the user to 'back out'. That is, once they have got to this point in the code, they  *have* to provide a valid input before they can do anything else - there is no option for them to say 'oops! didn't mean to do that' - and return to the previous point. This isn't a good  *experience* for them. At this point, we aren't in a position to do much about it - first because the programs we are writing are quite basic and only deal with text input. More importantly we haven't really introduced the right kind of Java features to make it practical to do something about this - but we will come back to this in the chapter on [Methods](https://canvas.swansea.ac.uk/courses/68227/modules/502607).

### 7.1.4 C1 Testing...

To test the code to safely read an integer between 1 and 100, we need to consider and follow these paths:

- The user entering a non-integer
- The user entering an integer between 1 and 100

We DON'T need to check the user entering an integer < 1 or > 100 - because the two cases above are enough to follow all the paths. But if it was me... I'd add checks for  *boundary conditions* 0 and 101 (or at least one of those).
