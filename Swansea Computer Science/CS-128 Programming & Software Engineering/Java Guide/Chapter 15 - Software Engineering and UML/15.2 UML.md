# 15.2 UML
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/15-dot-2-uml)

One of the issues we [mentioned earlier](https://canvas.swansea.ac.uk/courses/68227/pages/1-dot-10-programming-vs-software-engineering) was the fact that those involved in engineering software - the ones building it and the ones who wanted/asked for it - (collectively  *stakeholders* ) might not understand each other. It's common for there to be issues when trying to understand/explain technical issues, both between those who do and don't understand the issues, and  *between* those engineering systems. An important reason programming languages exist is that  *natural language* is not precise enough to say what we want to do - the classic example is "I saw someone on a hill with a telescope" - who has the telescope?

Various attempts have been made to address this, and a widely-used one is UML - the  *unified modelling language.* It's not actually a 'language' as such - it's a set of 14 possible types of  *diagram,* each of which is aimed at representing/explaining some different aspect of the software development process (and some are applicable to other kinds of project too). They essentially are categorised into  *behaviour/interaction* (which are useful for working out what you want/need in the first place - often a big problem); and structure (which are for describing how the different parts of a system relate to and interact with each other).

Not all the types of diagram are equally useful to us. Some are only really useful in specific kinds of project (e.g.  *timing diagrams* ) and others, though more generally useful are not so widely-used - they  *can* be useful, but often they are not needed (e.g. the problem can be solved easily without them). The three most widely-used are  *use-case diagrams; sequence diagrams;* and  *class diagrams.*

### 15.2.1 Use-Case Diagrams

These are meant to describe how a user (and there can be multiple different kinds of users) interact with a system. They are (deliberately) easy to understand because part of the point of them is to enable users of the system to understand them, interact with them, and help create them. So they deliberately avoid any complex terminology. Here's an example:

*(image on Canvas: Vending Machine Use-Case)*

The system is typically represented by a box (sometimes just a line down the image with the system on one side and the user(s) on the other) and the users by stick figures. In this case there is one user called 'user' but there could be different types (e.g. 'customer', 'admin' etc.). The actual use-cases (what you can do) are represented by ellipses (or circles sometimes), and any explanation is in rectangles. The only real 'notation' apart from that are <<include>> and <<extend>>, which (as explained on the diagram) represent things that will/must also happen; and things that  *could* happen.

What this diagram does NOT include is anything about  *how the system works.* It is  *entirely* about  *what it does.* That corresponds to the  *specification* phase of the software engineering process. A  *specification* is a solution proposed to a  *requirement -* which in this case might be 'we need someway for people to eat and/or drink', for which a vending machine is one possible solution and this is a specification of that solution. (Other possible solutions could be a cafe/restaurant, or a kitchen etc.).

### 15.2.2 Sequence Diagrams

One thing that is missing from the use-case diagram is any indication of the  *order* of events. And, in practice, there are clear orderings in the example above (dispense product will not happen before insert payment). Although it looks as if there is an ordering (down the image from top to bottom), in practice we need more detail before we can build anything. We might not need this for user/stakeholder, but we do to engineer a solution. We also probably need to start thinking about how the system will actually work, and so we need to be thinking about the major  *components.* Here's an example also based on a vending machine:

*(image on Canvas: Vending Machine Sequence Diagram)*

Here we are now clear about the order of events, but we have also made a  *design decision* to break the vending machine into four  *components.* The 'front end' vending machine itself which is essentially the  *user interface* ; the system that accepts payment; the system that keeps track of what is stocked in the machine; and the part that returns change. We have also labelled the arrows of which there are two different types - solid and dashed. So:

- In this case the solution translates into four main components -  **Vending Machine**,  **Payment Unit**,  **Inventory**  and  **Change Dispenser**  - which will probably end up as separate classes  *but that does not mean they will be the ONLY classes in the system.*
- The solid arrows represent  *calls* to methods in each of the classes. So you can see that when a user wants to see the available products, the **Vending Machine** 's  **getProducts()**  method will be called, and it in turn will call the Inventory classes  **getAvailableProducts()**  method.
- The dotted lines represent what is  *returned* be each method.
- In some cases (marked 'alt') different things might happen. So, for example, the  **checkAvailability**  method (Inventory) could return true or false - and depending on that, two possible actions happen ( **showPrice**  or  **informUnavailable** ).

This diagram basically defines what the solution consists of, what each part can do, and the order in which we expect things to happen.

### 15.2.3 Class Diagrams

A Class diagram is a  *class centric*  view (the main components are the classes) and it also shows the  *relationship* between each class. Although arguably it's something you should create to tell you how to write the code, they are commonly automatically-generated from the code itself (and IntelliJ can do that - see below). Either way, it gives you oversight of and insight into how classes are (or will be) related and what they can do (to each other), and it's an important tool in understanding the structure of the solution (either the one you have built, or the one you are going to build). Note we are treating the user as a class here (though with a different colour at the top).

*(image on Canvas: Vending Machine Class Diagram)*

This diagram does contain some things we have not done yet (e.g.  **Map** and  **enumeration** ). But essentially:

- Each box is a class - the things above the horizontal line are the  *data items* or  *fields* of the class; and the things under the line are  *methods.* In Java terms the + and - are  *access modifiers -* so - is  *private* and + is  *public.*
- The lines between classes represent  *relationships:*
		- Some of them have a word (a verb) that describes the relationship between the classes. These are generally  *domain specific -* that is, they depend on what you are doing and there is no pre-defined set of them.
		- Connecting lines describe  *relationships:*
		- Dotted lines are  *dependencies -* they mean if you change something at one end you will have to change the thing at the other end. This is the weakest possible relationship and in practice this is also true of all the other lines too.
		- Solid lines with no arrows or other things at the end are  *associations.* This means there is some kind of active connection (one of them doing something makes the other do something). In this case the only one is between the user and the user interface VendingMachine - because the user isn't 'code' then we can specifically imply that the user 'calls' anything (hence it's 'just' an association).
		- The diamonds - both empty and solid - represent 'has a' relationships, where the empty ones are called  *aggregations* and the solid ones  *compositions.* This is a bit beyond this module, but the solid ones represent a stronger relationship - and a simple way to view the distinction is to ask: if the one at the diamond end disappeared, what would happen to the other one? In reality the ChangeDispenser would contain the actual notes and coins, so if the  **ChangeDispenser**  disappeared then so would the notes and coins, so this is a  *composition.* But if the (user interface)  **VendingMachine**  class disappeared, the transactions would still exist (so this is  *aggregation* ).
		- Solid lines with an open arrow at the end are  *navigable associations -* that is, the one at the end without the arrow can 'call' something in the one with the arrow.  **VendingMachine**  can ask  **Product**  to dispense an item.
		- Solid lines with triangular arrows are  *inheritance.* We have not done that in this module, but in this case it means that the  *base class*  **Payment**  has three classes that  *inherit* from it and in this case  *extend* it with more capability. E.g. any kind of payment will need the  **getAmount**  method, but the  *type* of payment will mean other things are needed: for payment by cash, we need  **addCash**; by card we need  **authorise**; and to give  **change**  we need dispense. Rather than writing four separate classes that duplicate the methods (and data) common to them all; or writing one huge class that does everything, we write one base class with all the common code, and three others that inherit from that one ('this class does all the things that one does, plus these new extra things...)
- The various numbers are  *how many* objects of the relevant class there could possibly be. So there is only one  **VendingMachine**  object as it represents the user interface. But there could be between 0 (when the machine just starts up) and an unbounded number (represented by *) of  **Payment**  objects. So  **Payment**  is labelled  **0..*.**
