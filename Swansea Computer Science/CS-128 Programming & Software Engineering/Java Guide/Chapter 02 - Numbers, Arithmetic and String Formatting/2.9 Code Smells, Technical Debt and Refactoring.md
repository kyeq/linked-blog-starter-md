# 2.9 Code Smells, Technical Debt and Refactoring
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/2-dot-9-code-smells-technical-debt-and-refactoring)

“Any fool can write code that a computer can understand. Good programmers write code that humans can understand.”

— Martin Fowler

Here's a version of the swimming pool program in which I've included the String formatter from [section 2.7](https://canvas.swansea.ac.uk/courses/68227/pages/2-dot-7-string-formatter), the final variables from [section 2.8](https://canvas.swansea.ac.uk/courses/68227/pages/2-dot-8-non-static-final-variables), as well as slightly changing the computation of the cost of excavating the pool - I decided that the variable volume wasn't necessary as the code was simple enough without it. On the other hand, I think that the extra variables in the computation of the area of the pool (for tiling) makes it easy to understand, so I've left that in. (The code looks a bit different because the old online formatter I used has disappeared from the internet so I have to use a different one for anything new.)

```java
/*Program that estimates the cost of a swimming pool
 */
import java.util.Scanner;

public class SwimmingPoolEstimatorRefactored {

	//These values represent the costs of each phase
	static final int EXC_COST_PER_CUBIC_METRE = 20;
	static final int LINE_TILE_COST_PER_CUBIC_METRE = 25;
	static final int MACHINERY_COST = 1000;

	//The strings output by the program
	static final String DEPTH = "Enter the depth: ";
	static final String LENGTH = "Enter the length: ";
	static final String WIDTH = "Enter the width: ";
	static final String COST_OUTPUT = "Estimated cost: %s%n";

	public static void main(String[] args) {

		Scanner in = new Scanner(System.in);

		//Read in the pool size
		System.out.print(DEPTH);
		final int depth = in.nextInt();
		System.out.print(LENGTH);
		final int length = in.nextInt();
		System.out.print(WIDTH);
		final int width = in.nextInt();

		//Now calculate the excavation costs
		final int excCost = depth * width * length
			* EXC_COST_PER_CUBIC_METRE;

		//Calculate the lining/tiling costs
		final int baseArea = width * length;
		final int endArea = width * depth * 2; //Two ends
		final int sideArea = length * depth * 2;
		final int lineTileCost = (baseArea
			+ endArea + sideArea)
			* LINE_TILE_COST_PER_CUBIC_METRE;

		//Calculate the total cost
		final int totalCost = excCost
			+ lineTileCost + MACHINERY_COST;

		System.out.println(String.format(COST_OUTPUT, totalCost));
	}
}
```

Why do I keep messing around with the code and changing it?  *Hopefully* that is at least a bit clear - I've made the changes to try to improve the code. And by 'improve' I mean make more readable. I go on about readability a lot - but it's very important. In this section, I'm going to introduce three concepts that will hopefully help to make the reasons that this is so important clearer to you.

### 2.9.1 Code Smells

Looking at the core body of the program above:

```java
//Read in the pool size
System.out.print(DEPTH);
int depth = in.nextInt();
System.out.print(LENGTH);
int length = in.nextInt();
System.out.print(WIDTH);
int width = in.nextInt();

//Now calculate the excavation costs
int excCost = depth * width * length
	* EXC_COST_PER_CUBIC_METRE;

//Calculate the lining/tiling costs
int baseArea = width * length;
int endArea = width * depth * 2; //Two ends
int sideArea = length * depth * 2;
int lineTileCost = (baseArea
	+ endArea + sideArea)
	* LINE_TILE_COST_PER_CUBIC_METRE;

//Calculate the total cost
int totalCost = excCost
	+ lineTileCost + MACHINERY_COST;
```

We could just as well have written it, from Java's point of view (assuming we kept the constants), like this:

```java
//Read in the pool size
System.out.print(DEPTH);
int a = in.nextInt();
System.out.print(LENGTH);
int b = in.nextInt();
System.out.print(WIDTH);
int c = in.nextInt();

//Now calculate the excavation costs
int d = a * b * d
	* EXC_COST_PER_CUBIC_METRE;

//Calculate the lining/tiling costs
int e = c * b;
int f = c * a * 2; //Two ends
int g = b * a * 2;
int h = (d
	+ f + g)
	* LINE_TILE_COST_PER_CUBIC_METRE;

//Calculate the total cost
int i = d
	+ h + MACHINERY_COST;
```

But I hope you can see why this is a problem - it's a lot harder to understand what the second one means. Harder to read means it takes longer to read - which means it costs more to understand (time is money...), which means it's more expensive. It's But it isn't really any harder (or more expensive) to  *write* in the first place. Probably worse, because it's harder to understand, it's more likely to be  *misunderstood -* meaning someone may come along later and introduce changes that are wrong.

Bad variable names are an example of something called a  *code smell -* a concept introduced to from the expression "this code smells bad" - that is, it's not very good. We will come across other examples of  *code smells* throughout the module - things to be avoided because they are not good practice, and will may lead to problems later on. One of those problems is  *technical debt.*

### 2.9.2 Technical Debt

*Technical Debt* is like 'real' debt - it's something that will 'cost' you. Technical Debt will cost you time (and money) later on if you don't do something  *now* (just like 'real' debt the cost comes later - and the cost later is higher than the cost now). Suppose we wanted to increase the costs of our pool to something more realistic, and also to translate it into another language. Because we have taken the time and trouble to put in constants (static final variables) for the various costs and the messages,  *we only need to change this bit* :

```java
//These values represent the costs of each phase
static final int EXC_COST_PER_CUBIC_METRE = 50;
static final int LINE_TILE_COST_PER_CUBIC_METRE = 45;
static final int MACHINERY_COST = 1700;

//The strings output by the program
static final String DEPTH = "Βάθος: ";
static final String LENGTH = "Μήκος: ";
static final String WIDTH = "Πλάτος: ";
static final String COST_OUTPUT = "Κόστος: %s%n";
```

If we  *hadn't* done that, we would be hunting through the code, finding the messages and the numbers (and taking time to check that the numbers really were the ones we needed to change - or risk introducing errors). In this simple example, it wouldn't take very long: but in a real program many thousands of lines long, it would be a very expensive task. (Apologies to any Greek speakers - I'm only reasonably sure this is correct.)

### 2.9.3 Refactoring

Making changes to code in the way we have is called  *refactoring -* it's the process of thinking (or  *reflecting* ) 'how good is this code and can I make it better?' Professional programmers who do it write code that is easier for others (and them) to read, understand and - critically *change later on. All* real-world code ends up being changed (or  *maintained* ) during its life. Writing it well to start with makes that easier - it reduces the  *technical debt.* It also often helps you spot bugs you otherwise wouldn't.

So when you are programming, divide your time between working on the code, and stepping back and thinking 'how can I make this code better?' - this is sometimes called  *two hats:* because you are wearing two 'hats' - the programmer's hat and the 'quality control' hat.

### 2.9.4 Refactoring Patterns

One thing we often do in programming is identify  *patterns -* things or approaches we use a lot. This is the same as any other kind of engineering - bridges for example fall into a set of different types and you can see this simply by looking at them:

*(image on Canvas: Types of bridges)*

It's rare that anyone tries to build one that doesn't fit into the commonly-used patterns of bridges, and when they it usually involves a few cautious changes.

We can identify patterns in refactoring - and doing this helps us to look for things that we could sensibly change. We have seen three common patterns so far.

- **Renaming a variable**  - consider if the name you have given a variable best explains what it does. If it doesn't, then rename it. (Software development tools often have ways of automatically and systematically doing this because it's so common).
- **Introduce a variable**  - and...
- **Remove a variable** - the changes we made when we removed the variables called depth, width, length and volume are examples of removing a variable; doing the reverse is introducing a variable.

Obviously, if we have two refactoring patterns that do the exact opposite things, then there is no one way to write our programs that will always work. You will have to use your judgement - and the more you practice ,the better your judgement will get.
