# 2.10 Introduction to Testing
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/2-dot-10-introduction-to-testing)

The swimming pool example just does simple calculations, and does exactly the same calculations each time - as long as the user enters the correct kind of data (and we'll get to how you properly check that [later](https://canvas.swansea.ac.uk/courses/68227/modules/502605)) then it will just perform the same calculation. This means it's pretty easy to test - it always does the same thing every time. We will next be seeing programs where that isn't true. But even in cases like the swimming pool program -  *straight line programs -* this isn't always true:

```java
public class FairShare {
    public static void main(String[] args) {
        Scanner input = new Scanner(System.in);
        System.out.print("Enter the number of chocolates: ");
        int chocolates = input.nextInt();
        System.out.print("Enter the number of people: ");
        int people = input.nextInt();
         ("Each person gets " + chocolates/people + " chocolates");
    }
}
```

Suppose you enter zero for the number of people - you will get a  *divide by zero* error:

```java
Enter the number of chocolates: 20
Enter the number of people: 0
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at FairShare.main(FairShare.java:10)
```

So even quite simple programs may need more testing than you might think. Testing forms a very large part of the budget of software projects - up to 50% for 'normal' projects and 90% for  *safety critical* projects. It is a sophisticated and complex process and many new Computer Science graduates start their careers as  *test engineers.*

### 2.10.1 Types of Testing

Software testing is a very sophisticated practice, and often overlooked in introductory programming - so we are going to start taking it seriously, and include information on testing types and good practice from now on in most sections of this module.

We can categorise testing in a number of different ways. First by what we assume we know about the program under test.

- **Structural Testing.** This kind of testing allows us to take account of the way the code works - we base the tests we build on how the code is written. This is the kind of testing we are going to focus on in this module and it was historically called  *white box testing.* We are moving away from terminology like that, and the usual modern name is  *structural testing.*
- **Functional Testing.**  This kind of testing does not allow us to make any assumptions about  *how* the code works - we just base the testing on  *what the code is supposed to do.*  Which of course is what a user of the code is interested in. We are not going to look at this here, but you will in the follow-on module in the second semester. Historically this was called  *black box testing -* but, again, we are moving away from that term.
- In this module we are going to do structural testing; you will do functional testing in CS-129 in the 2nd semester.

We can also categorise testing in relation to what they are meant to achieve - and some kinds of tests can fall into more than one of the categories below (which is a list of the main types - there are more):

- **Unit Testing**. This is about testing small parts of your code, and you would typically do this as the actual developer - rather than it being done separately by someone (or something) else. When done properly this involves writing  *test code* BEFORE writing the actual code you want to test. There are libraries in Java to support this (and they are directly supported by IntelliJ for example).
- **Integration Testing.**  This is done when combining multiple systems together to ensure that they work.
- **Acceptance Testing.**  Essentially a pass/fail process to decide if a system correctly does what it was designed to do (and possibly that a customer paid for it to do).
- **Regression Testing.**  Tests that you repeatedly re-run (say daily) to ensure that changes you have made to a system have not 'broken' anything that was previously working.
- **Smoke, or Sanity, Testing**. Basic testing to decide if a system is working well enough that it's worth the effort of doing more intensive or detailed tests.
- **Automated Testing.** All of the above testing types (and other testing types, not listed above) can be  *automated.* That is, rather than you having to do them manually,  *other code that is written*  *solely for testing* decides if the code under test passes the tests or not.

There are some other important points to know about testing.

- **Debugging**  is not the same as testing! Testing is essentially a pass/fail process, that you might use as a way of deciding if a bug, or bugs, are present - and so you would then go on to debug the code.
- **Test Code is Important.** Something it says somewhere else in the notes - most testing needs you (or someone) to write  *other* code, just for testing. It can take a while to get past the idea that this is a 'waste' of effort.  *But it is not!* Writing test code to systematically and automatically test your code, will  *reduce* the time and effort you need to spend.
- **Boundary Conditions.**  The 'fair share' example above only fails, arguably, when the number of people is zero. It will also fail if you type in things other than integers (but we haven't seen how to fix that yet, so we will ignore it); and it will also give silly examples if you enter negative numbers (though it won't crash). So, essentially it works if you enter, a positive number ...5, 4, 3, 2, 1 etc. for the number of people, or if you enter a negative number -1, -2, -3, -4, -5,... - but it  *doesn't* work if you enter 0: the result changes when you change the input from 1 to 0 (or from -1 to 0). There is a kind of 'boundary' between these numbers when the performance of the program changes - and we call this a  *boundary condition:*  remember the 'green bus' above. It is common to run into problems caused by boundary conditions, and we put a lot of effort into testing those.
- **YOU NEED TO KNOW WHAT THE TEST RESULT SHOULD BE BEFORE YOU START!** This is so important and often overlooked - you write some code, and try some test values - but don't really know in advance what the results should be. So how do you know if it works or not.
