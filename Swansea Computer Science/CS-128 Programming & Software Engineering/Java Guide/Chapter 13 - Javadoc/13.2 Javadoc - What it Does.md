# 13.2 Javadoc - What it Does
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/13-dot-2-javadoc-what-it-does)

The traditional way of doing ‘what it does’ documentation was to write separate documents – but this is not good for four reasons:

- **Wasteful**  – at least some of the things you need to write in these documents are already in the code.
- **Goes out of date**  – if you change the code you need to change the documentation and you’ll often forget.
- **Extra documents to maintain**  – as well as the code, you now have more documents to deal with.
- **Contradictory** - because it's a separate document, it's easy to write things that actually contradict the code (this is related to the point about being out of date above).

Now more usually there are tools that allow us to write the documentation as part of the program, not repeating anything from the code itself (that is extracted automatically), meaning there is only one document (the code) to maintain, and because you see it whenever you edit the code, it's harder to forget to update it. Because it uses a  *tool* to actually then generate the documentation, it's able to do e.g. error checks, to ensure you haven't done anything contradictory (within limits).

which is the documentation for one of the get() methods. Clearly, someone has been to a lot of trouble to write all this – and they have, but not as much as you think, because it’s generated from the code with a few ‘special’ comments.

Depending on what software you have used to write code, you may already have seen some basic examples of what these look like:

```java
/**
 *
 * @author neal
 */
public class SomeJavaApplication {

	/**
	 * @param args the command line arguments
	 */
	public static void main(String[] args) {
	    //TO-DO - write code
	}
}
```

As well as the obvious  *attributes* starting with '@', you can see that the comments start /** instead of just /*. This marks these comments as  *Javadoc*  comments, which can be processed by the  **javadoc**  tool to generate documentation.

The way we create this documentation is to add these specially-formatted comments in appropriate places, and use specific attributes to identify and format the content. The  **javadoc** tool then extracts information from these comments  *and the code* to create the documentation. This is:

- **Less wasteful**  – as we’ll see information that can be extracted from the source code is: we don’t have to write it out again.
- **More likely to update**  – it doesn’t force you to update it, but you are more likely to if you are looking at it at the same time you’re editing the code
- **No extra documents**  – obviously, as it’s in the code.

### 13.2.1 REFACTORABLE!

This is a MASSIVE one. If you, say, change the name of a method in code and the documentation is separate, odds are good that you will forget to update the documentation. Of course that could also be true if you use Javadoc. EXCEPT THAT:

- IF you use a tool like e.g. IntelliJ
- AND when you rename things in your code you use the  *refactoring* tools instead of just manually renaming things
- THEN your documentation gets updated automatically!
