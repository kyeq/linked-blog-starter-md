# 13.1 Kinds of Documentation
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/13-dot-1-kinds-of-documentation)

We can distinguish between several types of documentation.

- **How it works**  – this is documentation that explains how our code works. It’s for people who work on maintaining it and developing it.
- **Version History**  – this is a list of all the changes that were made to code from one version, or release, to the next. It’s meant for both users and developers.
- **What it does**  – this is documentation mainly meant for those who are using the code and don’t need to know how it works.

### 13.1.1 Different Types, Different Approaches

There are several ways we can do each of these – but we’ll just look at one ortwo in each case.

**How it Works – Good Code + Standard Commenting**

In order to explain how your code works you should write and lay it out in a clear way, put readability above showing off, and choose your names carefully. You should also comment your code. There are no strict rules to this but (and we have seen this already in this module):

- Comment each variable declaration if it’s not obvious. You might want to alternatively consider commenting a 'block' of related variables.
- Comment each logical block of code – for example, each method (though see below).
- Comment anything tricky – if you found it hard to write, or can see that it’s not obvious how it works, or that there are things someone needs to be careful about before making changes, then comment it.

### 13.1.2. Self-Documenting Code

Occasionally (though not so much anymore) you get statements like:

*“I don’t need to comment my code – it’s self-documenting”*

By this, the programmer means that they believe they are so good at writing clear code that no further commenting is necessary. This is, as well as being arrogant, an extreme position to take – it’s true good, well-laid out designed code with good identifier names doesn’t need as much commenting. But it’s a fallacy to claim it never does. So don’t do it:-)

### 13.1.3. Version History – Version Control System

In a ‘real’ application (or, say, a 2nd year software engineering project; or 3rd/4th year project) you are likely to be using a  *source code control system* : a piece of software that maintains a history of your code (including  *versioning* and the ability to  *roll back*  to previous versions), and also – usually – includes tools so multiple programmers can collaborate on applications. Systems like this include  *GitHub*  (and there are others). I know some of you will already be using these. These systems also include tools that let you enter version information and, often, maintain version numbering systems (so you don’t have to) - they generally encourage (or require) you to document the changes you are making when you  *commit* a new version of your code. It’s also possible to use the tools we’re going to talk about next to do this.

### 13.1.4 Documentary Comments

The main kind of commenting we are interested in this chapter is those that tell you how to  *use* code - not as an end user, but as another programmer.
