# 14.3 Maven Build Tool
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/14-dot-3-maven-build-tool)

Before we actually look at unit testing and [JUnit](https://junit.org) we need to cover how we are actually going to get this to work, because although a very commonly used and essentially 'standard' thing, JUnit, is  *not* built into Java, so we need to add it as a  *library* or  *API* (application program interface). The easiest way to do this is to use a  *build tool -* one that's built-in to IntelliJ

### 14.3.1 Build Tools

A build tool just controls how applications are created from the source code and any other data/files that's needed - which so far for us has just meant "compile all the Java files". E.g. javac HelloWorld.java is a very simple build tool; if you have more than one Java file and you are not using e.g. IntelliJ then you might do javac *.java to compile all your Java files. This is fine if all you have is a few Java files in one folder, but usually applications are more structured with multiple folders and, critically, API or library code. You can do that directly, but you need to manually download the libraries, put them in the right place, and tell Java where they are. Modern build tools handle all that using a  *configuration file -* you just say what you want and it handles the details. IntelliJ has a standard built-in tool that it uses, but to get Junit working, we need something more advanced and we will use [Maven](https://maven.apache.org).

### 14.3.4 Unit Testing

The basic idea of unit testing is very simple - creating tests for individual and usually small  *units* of code, so we test them in isolation, so we know that they work (or are pretty sure at least) before we start combining them together. That way, it's more likely that errors are a result of  *integrating* the smaller units of code, and so we can focus on looking at how those units of code interact to find problems, rather than worrying that the units themselves may be faulty. This is not perfect of course:

- Testing is usually not exhaustive even for small blocks of code - [we have already seen that.](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-8-basics-and-problems-of-testing)
- You may not know exactly how the code is going to be used so the tests may not be realistic. For example, you may assume that some operation will only happen when, say, some value is positive - so you don't test it when it's negative.

But, in general, this is a very well-established model and the usual way it works is that the  *programmer* writing the code does the unit testing (as opposed to more high-level tests, like  *integration* or  *regression* testing, where it's more likely to be a test engineer, or team of test engineers).

For us a 'unit' is going to be a  *class.*
