### 14.4.1 Annotations

You can use a wide range of  *annotations* (things beginning with '@') in JUnit, though only a few will be really useful for us in this module.

**@Test**  - The most important one - marks the method that follows it as a test case that can either pass or fail.

**@BeforeEach** - Marks a method to be run before  *every* test. This is generally used for code that 'sets up' a test (for example, creating a number of objects for the tests to be run on) and, because it's run every time, it means you start each test with 'fresh' data. You  *can* just repeat the code in every test, but that will obviously duplicate code and make any changes you want to make to the set up code more difficult and time consuming.

#### Other Annotations

For us, these two are basically enough but there are others you would want to use in practice once you do more advanced programming.

**@DisplayName**  - actually this is something we  *would* like to use here because it lets us give tests a meaningful name (e.g. @DisplayName("Test the withdrawMoney method"). Unfortunately IntelliJ does not use it so there isn't much point - you can if you want put it in if you think you will be running tests outside IntelliJ. You almost certainly won't in this module, but it would be quite likely professionally.

**@Disabled** - again not used by IntelliJ. It lets you mark a test as not being used (which usually means you haven't finished writing it yet).

**@BeforeAll**  - unlike @BeforeEach this is only run  *once* before all tests are run. You would do this if either: (a) there is some setup that does not need to be repeated; or (b) if you are running tests in a sequence where one test assumes another one has already run (e.g. one test might withdraw money from an account so the balance is zero, so a later test can delete the account). NOTE THOUGH that  *strict* unit testing does not allow (b) - tests should be independent - and also JUnit does not guarantee the order tests are run in unless you use  *another* annotation  **@TestMethodOrder**. This is all getting too complicated for us in this module.

**A Lot of Others...**  There are many other possible annotations and we are not going to list them - they are beyond the scope of this module.

### 14.4.2 Assertions

We need some way of checking if tests have been passed or failed, and the way to do that is to  *assert* something is true - and the test will pass if it is, and fail if it isn't.

assert keyword

The simplest way to do this is a built-in Java keyword  **assert**  - you just need to give it a boolean expression:

```java
assert(bankAccountBob.getBalance() == 0);
```

If the boolean expression is true, then nothing happens - if it's false, then you get an 'assertion failed' message.

That, strictly is all you need. But there is an Assertions class that contains many others, all of which internally use assert. It was one of these -  **Assertions.assertEquals**  - that we used in the video above.

Others include:

**Assertions.assertEquals**  - this is the one we used in the video above, and it looks as if it doesn't do anything that assert does not. But you can give it message to output when there is an error. e.g.

```java
Assertions.assertEquals(bankAccountBob.getBalance(), 50,
                "Balance should be equal to zero");
```

which will, if it fails, say something like this:

```java
org.opentest4j.AssertionFailedError: Balance should be equal to zero ==>
```

followed by information like e.g. the line number.

Similarly, most of the others also include the option to output a message:

- **Assertions.assertTrue**  - the statement is true e.g.  **Assertions.assertTrue(0 > 1, "Amazing!!! 0 is not bigger than 1!!!");**
- **Assertions.assertFalse**  - as above but false not true
- **Assertions.assertNull**  - as above but instead of true/false this is true if the first argument is null.
- **Assertions.assertNotNull**  - as above but not null instead of null
- **Assertions.assertArrayEquals**  - as above but compares two arrays for equality element-by-element (this would actually be a bit more tricky with 'ordinary' assert).
- **Assertions.assertSame**  - as above but checks if the two things compared are  *the same object* - not just that they are equal. (To understand how this is different to  **aAssertions.assertEquals**  consider comparing two strings - using == e.g.  **string1 == string2**  is checking if the two strings are the same object which is what  **assertSame**  does. But  **string1.equals(string2)**  checks if they have the same  *value* which is what  **Assertions.**  **assertEquals**  does).
- **Assertions.assertNotSame**  - as above but not the same object.

There are quite a few more but they involve Java and programming concepts out of the scope of this module.

### 14.4.4 Mocking and Dependency Injection

One issue mentioned in the video above is - what about when you are testing something that depends on something else? In the case of  **Bank**, this is  **BankAccount**. In this particular example, we can reasonable say that we would have written a set of tests for  **BankAccount**  separately because both classes are pretty simple. But in reality, this will not be so simple - the combination of classes you might need to test could be complex; or you could simply not be the author of some parts of the code that you need for your testing. The usual solution to this is  *mocking -* making a 'mock' simplified version of the code instead of using the actual version. This limits the issues you have to deal with, because - as it's simplified - the mocked-up code does not introduce potential complexities or issues, and allows you to test the code you are working on independently (or as independently as possible). There are libraries and applications that help you mock-up test code - though we are not going to get into them here.

Related to this is the problem of how to test something when it relies on something else - which you (or someone...) may not have written yet; or tested yet; or debugged yet; or may just be very complex and would make testing your code difficult. The basic idea of the problem is here:

```java
public class WantToTestThis {

	public ComplicatedThingNotWrittenYet thing; //Or not tested yet, or has complicated behaviour...

	public WantToTestThis() {
		thing = new ComplicatedThingNotWrittenYet();
	}
}

//Make it like this
WantToTestThis somethingImportant = new WantToTestThis();
```

The problem is that we would need to edit  **WantToTestThis**  in some way to actually test it without dealing with  **ComplicatedThingNotWrittenYet**. A solution to this is to re-write the code using  *dependency injection -* not directly embedding the problematic complicated thing in our code. The basic idea is:

```java
public class WantToTestThis {

	public ComplicatedThingNotWrittenYet thing; //Or not tested yet, or has complicated behaviour...

	public WantToTestThis(ComplicatedThingInterface thingReference) {
		thing = thingReference;
	}
}

//Make it like this
WantToTestThis somethingImportant = WantToTestThis(myRealComplicatedThing);
//Test it like this
WantToTestThis somethingImportant = WantToTestThis(mySimpleMockTestThing);
```

Now we can test it using a simplified,  *mocked,* version of the  **ComplicatedThingNotWrittenYet**. And we don't have to make any changes to  **WantToTestThis**  to do that. This does require a concept you have not seen yet called an  *interface* (not to be confused with user interface) - this is something you will do in Semester 2.

### 14.4.5 Good Practice

When you are writing unit tests it's important to understand what the point is - it is  *not* to find bugs in existing code: it's to design and write the code properly in the first place. So

#### Ideally, write the unit tests first.

Usually, you would have one or more tests for a method in a class - and you would know what the  *signature* of the method you want to write is: name, parameters, what it returns. So before you write the method, think though what the outcome of the method would be, and what needs to be true before you run it. For example:

```java
public Double divide(double dividend, double divisor) {
	//code to do
}
```

Which is a method we are going to write to do division - but one that specifically returns a Double (capital D) because it's going to return null if we attempt to divide by zero. So we might want to test:

that we do get null if we try to divide by zero- this is something we would call a  *pre-condition:* something that  *has* to be true for the test to be meaningful.

that the result is equal to dividend/divisor if we don't try to divide by zero - this is something we would call a  *post-condition:* something that has to be true  *after* the code is run.

So we get something like:

```java
@Test
public void divideTestNonZeroArgs() {
	Assertions.assertEquals(10/5, divide(10,5), "divide: result of division not correct with non-zero divisor");
}

@Test
public void divideTestZeroDivisor() {
	Assertions.assertEquals(null, divide(10,0), "divide: result not null with zero divisor");
}

@Test
public void divideTestZeroDividend() {
	Assertions.assertEquals(0, divide(0,10), "divide: result non-zero for zero dividend");
}
```

This is arguably a bit much for a simple division method (which we probably wouldn't bother to write anyway) - but notice we have done this  *without* having written the code for divide (exercise...) - by thinking through first what it  *should* do.

#### Key Point: Design not Debugging

Unit testing is about correctly designing the code in the first place - not about debugging it later on. Having said that, it can find bugs when you refactor - later make changes to the code and introduce bugs.

#### Separate Tests for Separate Things

We have three separate tests for a simple divide method - which looks a bit excessive (and TBH it probably is). But we did it this way instead of combining them into one to illustrate the point that separate things should be tested separately. In this case, you could probably argue the thing you should be testing is 'divide works properly' and just put all three assertions in one test method. But in more complex and realistic cases, you would not (or should not) do that.
