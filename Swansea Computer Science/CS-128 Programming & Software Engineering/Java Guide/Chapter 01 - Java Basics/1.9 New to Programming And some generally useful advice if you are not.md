# 1.9 New to Programming? And some generally useful advice if you are not...
> [!info] From the CS-128 notes on Canvas — [open the original page](https://canvas.swansea.ac.uk/courses/68227/pages/1-dot-9-new-to-programming-and-some-generally-useful-advice-if-you-are-not-dot-dot-dot)

If you are new to programming then this can all seem to be a bit intimidating - and it WILL be more work for you. But there is no statistically significant difference in outcomes - some years those with previous experience do a bit better; and some years it's actually the other way around. But the differences are always small and the correlation is very weak.

There are two things that you are likely to find need work.

- Learning the terminology (the  *syntax)* of the language.
- Learning how to actually turn problems into programs.

The first one is work for  *everybody -* and is usually the reason those who have programmed before do less well than they should (overconfidence essentially).  *Everybody* needs to put the time in for this.

The second on is trickier and below are some strategies to help you.

### 1.9.1 What Programming Languages can do

It helps to remember that there are some basic things programming languages can do:

- One thing followed by another thing. So, for example, "first crack the eggs into a bowl, and then whisk them" - this is two things, one after another.
- One thing or another thing. So for example, "if you are using a fan oven, set the temperature to 180, else set it to 200". There is a  *choice* here and the decision is based on a  *condition* - something that is either true or false (you either have a fan oven or you don't).
- One thing over and over again until something happens to stop it. So for example, "whisk the egg whites until they become stiff and form soft peaks"
- Store data. So for example, "Take the sugar and split it into thirds to use later".

Programming languages have more capabilities than this  *but they are all really about making life easier and don't let them do more -* so knowing those things above is enough to use them to solve problems.

### 1.9.2 Divide and Conquer

Problems can look overwhelming at first - they are just too big and complicated to solve.  ***So don't.***

- Break them into parts - the examples above come from a recipe for [meringue](https://en.wikipedia.org/wiki/Meringue) - which has eight steps. So "make a meringue" (which is complicated) is divided into eight small steps (each of which is simple).
- Do what you can -if you can't see how to break up the  *whole* problem into parts, find one you  *can* do - ideally the first step but it doesn't have to be. And just do that (often the next step becomes clearer once you do that).
- Don't get "sucked in" - this is something that we will [come back to later](https://canvas.swansea.ac.uk/courses/68227/pages/4-dot-4-complex-conditions-and-nested-if-statements) (go to the last video) but it means that it's easy to end up getting sidetracked and solving other problems while you are trying to do something: usually because you think you "need" the solution to that other (side) problem to solve the one you are doing. Well you probably do  *eventually - but NOT NOW.* Try  *really hard* to not get distracted. E.g. suppose you are writing a program to calculate currency conversion rates - you might think "well I need to go away and actually get the exchange rates". Yes -  *eventually -* but for now just put in a plausible number so you can finish and test the solution  *to what you are doing right now.*

### 1.9.3 Remember - Be Patient

Be patient about two things:

- Yourself for not instantly being able to do this - it takes time and practice (but you do have to put in the time to practice - it it won't get any better if you don't).
- Even once you've done the practice, not immediately being able to come up with a good solution. This is true for everybody - you have to try things; experiment; look for improvements. Anyone who does not do this regardless of their experience is not going to be coming up with consistently good solutions.

### 1.9.4 Write it out in Words

Just write down the solution to the problem in natural (written) language - it can be whatever language you want, though it helps to think in terms of the list above - try to write it out in terms of the four things a language can do: one thing followed by another thing; one thing or another thing; one thing repeated until something happens; and storing (remembering/keeping) things for later.

### 1.9.5 Pseudocode

Instead of writing it out in Java you can use  *pseudocode -* this means different things to different people, but for you it makes sense to think of it as a mix of actual Java and natural language. So you write some of your solution in Java (or something like Java) and some in natural language. There's a description on [Wikipedia](https://en.wikipedia.org/wiki/Pseudocode) but it's not hugely helpful other than the statement "Pseudocode generally does not actually obey the syntax rules of any particular language; there is no systematic standard form." In other words you can make up whatever you want to help you to turn solution to the problem you are trying to solve into code, in stages.

### 1.9.6 Combine the Two

Another thing that can help is to use the two approaches above - first write it out in natural language, and then in stages turn each part into pseudocode and then Java.

### 1.9.7 Flowcharts

Instead of using natural language you can do this graphically by using a  *flowchart.* Flowcharts are a standardised way of writing out processes or algorithms and have a quite complex syntax. But you can just restrict yourself to three things.

- Rectangular boxes - that contain  *actions* or  *processes* (things your program will do).
- Diamonds - that contain  *decisions* (usually written as questions that are either true or not e.g. "Is it a fan oven?"
- Arrows - that link the boxes and diamonds (formally called  *flow lines* but that's not important).

You can see a couple of examples on the [Wikipedia](https://en.wikipedia.org/wiki/Flowchart) page for flowcharts BUT BEWARE!! There is one serious problem with flowcharts that isn't going to be obvious right now but you can see in the second example on the Wikipedia page: the one representing a "C-style loop" (which is the same as one you can use in Java). Instead of representing this action as a  *structured* component (a loop) it represents it as a decision (diamond) and two arrows they either jump to the end of the flowchart or back to the decision. This can encourage you to do things in a less than good way. But TBH, that's a problem for Chapter 6 onwards, not right now - so if flowcharts help you think through problems right now, then use them.
